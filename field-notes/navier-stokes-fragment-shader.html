Solving Navier–Stokes equations in a fragment shader

Building AETHER: a fluid simulation that turns pointer movement into light, momentum, and sound.

Launch Aether

AETHER began with a simple question: could a cursor leave behind something that felt less like a trail and more like a material?

I did not want another particle system made from circles politely following the pointer. I wanted the screen to behave like a continuous field—something with pressure, turbulence, momentum, and memory. That meant borrowing a small, practical slice of computational fluid dynamics.

Why this belongs on the GPU

A fluid grid becomes expensive almost immediately. A 512 × 512 simulation contains 262,144 cells. Every frame, each cell samples several neighbours while transporting velocity, calculating divergence, solving pressure, and moving density. Repeat the pressure solve twenty times and the browser is already doing millions of related operations.

JavaScript executes most of that work sequentially. A GPU is built to run the same operation across thousands of values simultaneously. A fragment shader normally decides the colour of a pixel; in AETHER, each fragment represents one cell in a numerical field.

The display is an image. The simulation is also an image—except its channels contain velocity, pressure, and density instead of red, green, and blue.

Each simulation step is a fullscreen draw call. The output texture from one shader becomes the input for the next. At the end, a final shader interprets the density field as colour.

Turning the equation into passes

The incompressible Navier–Stokes equations can be written as:

∂u/∂t + (u · ∇)u = −∇p + ν∇²u + f
∇ · u = 0

Here, u is velocity, p is pressure, ν is viscosity, and f represents an external force—such as a pointer moving through the field. The compact notation hides several distinct jobs, so I split the simulation into discrete rendering passes:

  1. Inject pointer velocity and colour density.
  2. Advect the velocity field.
  3. Diffuse velocity where viscosity is required.
  4. Measure divergence.
  5. Iteratively solve for pressure.
  6. Subtract the pressure gradient from velocity.
  7. Advect density through the corrected velocity field.
  8. Render the resulting field to the screen.

This follows Jos Stam’s “stable fluids” approach: it favours stability and interactivity over physically exact turbulence. For an instrument running inside a portfolio, that is the correct trade.

Advection: tracing every cell backwards

Advection asks where the material currently occupying a cell came from. Pushing values forward creates gaps and race conditions, so the shader traces each fragment backwards through the velocity field and samples the source there. 

precision highp float;

uniform sampler2D uVelocity;
uniform sampler2D uSource;
uniform vec2 uTexelSize;
uniform float uDeltaTime;
uniform float uDissipation;

varying vec2 vUv;

void main() {
  vec2 velocity = texture2D(uVelocity, vUv).xy;
  vec2 previousPosition =
    vUv - velocity * uTexelSize * uDeltaTime;

  vec4 transported =
    texture2D(uSource, previousPosition);

  gl_FragColor = transported * uDissipation;
}

This semi-Lagrangian method remains stable when the frame time shifts slightly. It does lose energy, but the loss is useful here: the visual field gradually settles instead of accumulating motion forever.

Projection: removing artificial compression

After forces and advection, parts of the velocity field may expand or contract. An incompressible fluid should not spontaneously create or destroy volume. I first calculate divergence by comparing opposite neighbours: 

float left   = sampleVelocity(-1.0,  0.0).x;
float right  = sampleVelocity( 1.0,  0.0).x;
float bottom = sampleVelocity( 0.0, -1.0).y;
float top    = sampleVelocity( 0.0,  1.0).y;

float divergence =
  0.5 * ((right - left) + (top - bottom));

gl_FragColor = vec4(divergence, 0.0, 0.0, 1.0);

Divergence identifies the cells where velocity is flowing inward or outward. The next shader approximates the pressure required to cancel it. A Jacobi iteration samples the four neighbouring pressure values: 

float pL = samplePressure(-1.0,  0.0);
float pR = samplePressure( 1.0,  0.0);
float pB = samplePressure( 0.0, -1.0);
float pT = samplePressure( 0.0,  1.0);

float divergence = texture2D(uDivergence, vUv).x;
float pressure = (pL + pR + pB + pT - divergence) * 0.25;

gl_FragColor = vec4(pressure, 0.0, 0.0, 1.0);

One pass is only a rough estimate. Repeating it between fifteen and forty times lets pressure propagate across the grid. Finally, subtracting the pressure gradient from velocity leaves a near-divergence-free field. That projection step creates the rolling curls that make AETHER feel fluid rather than merely blurred.

Textures as simulation memory

A shader cannot safely read from and write to the same texture during one pass. Every field therefore owns two textures and two framebuffers—a pattern usually called ping-pong rendering. 

class DoubleBuffer {
  constructor(read, write) {
    this.read = read;
    this.write = write;
  }

  swap() {
    [this.read, this.write] = [this.write, this.read];
  }
}

renderPass({
  program: advectionProgram,
  input: velocity.read.texture,
  target: velocity.write.framebuffer
});

velocity.swap();

In WebGL2, velocity can live in an RG16F texture, density in RGBA16F, and pressure and divergence in R16F. Floating-point storage matters because these fields require signed values and more precision than an ordinary eight-bit colour texture provides.

Simulation resolution is the strongest performance lever. The canvas may be 1800 pixels wide while the fluid grid is only 512. Bilinear filtering hides much of the difference while saving millions of texture reads per second.

Turning gesture into force

Pointer movement arrives in CSS pixels, while the fluid lives in normalized texture coordinates. I calculate a velocity vector from consecutive events, normalize the position, and inject a radial “splat” into the velocity and density buffers. 

const dx = pointer.x - pointer.previousX;
const dy = pointer.y - pointer.previousY;
const speed = Math.hypot(dx, dy);

splat({
  position: [
    pointer.x / width,
    1 - pointer.y / height
  ],
  velocity: [
    dx * forceScale,
    -dy * forceScale
  ],
  radius: baseRadius + speed * radiusScale
});

Slow movement creates controlled ribbons. Fast movement injects more momentum and generates turbulence. If every event applied the same force, the interaction would feel binary; mapping force to speed gives the gesture weight.

The mathematical chaos is the interface

Visitors do not need to know that AETHER contains a pressure solver. The value of the mathematics is the continuity it creates between intention and response.

Move slowly and the field stretches. Accelerate and it folds. Stop and the fluid keeps travelling before gradually losing energy. The interface does not merely acknowledge input; it interprets it.

A conventional animation plays a result decided in advance. A simulation creates a space of possible results. I define the laws, palette, dissipation, scale, and boundaries. The visitor composes the final image through movement.

The chaos is genuine. The frame around it is designed.
